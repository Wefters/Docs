```bash
wefter create-plugin secure-storage
```

generates a working, buildable-as-is starting point, both platforms, that
passes `wefter plugin validate` immediately, with zero edits:

```
secure-storage/
├── package.json
├── plugin.json
├── README.md
├── src/
│   └── index.ts
├── android/
│   └── SecureStoragePlugin.kt
└── ios/
    └── SecureStoragePlugin.swift
```

Full argument reference and every generated file shown in full:
[`wefter create-plugin`](/cli/create-plugin) on the CLI tab. This page
covers the one thing worth understanding deeply before you start editing
what it generated.

## The namespace constraint: Android only, and absolute

<Callout type="warn">
  Never change the `package dev.wefter.bridge` line at the top of any
  `.kt` file under `android/`, even though it isn't your plugin's real
  package and never will be.
</Callout>

Every Wefter plugin's Android source is authored against this one fixed
placeholder package on purpose, so a plugin author never has to know
which namespace any particular host app will actually use. When
[`wefter sync`](/cli/sync) weaves your plugin into a host app, it does a
literal string replace of `package dev.wefter.bridge` for every `.kt`
file it copies in, nothing smarter than that, just a direct text
substitution (`copyAndroidNativeSource` in `@wefterjs/registry-codegen`,
the same rewrite the generated shell itself goes through).

Rename that line to anything else, even something that looks more
"correct" for your plugin, and the rewrite has nothing to match. Your
file gets copied in with whatever package you wrote, the class ends up
outside the namespace the generated registry expects it in, and the
woven project fails to build. The class name itself
(`SecureStoragePlugin`) is yours to change freely, only the `package`
line is off-limits.

<Callout type="info">
  There's no equivalent constraint on `.swift` files, and nothing to
  leave alone there. `sync` copies `ios/*.swift` in verbatim, no string
  replace of any kind. Swift plugin classes compile straight into the
  one fixed `WefterBridge` app target regardless of which host app they
  end up in, so there's no per-app identity for the source to need
  rewriting into. If you're looking for the Swift equivalent of this
  rule, there isn't one; that's not an oversight.
</Callout>

This exact mistake, renaming the package line because it looks
wrong, was caught before it ever shipped to a real plugin author. This
page exists partly so nobody has to rediscover it the hard way a second
time. The [`wefter create-plugin`](/cli/create-plugin) page on the CLI
tab carries the identical warning; landing on either page first should
get you the same answer.

## Next steps

```bash
wefter plugin validate ./secure-storage
```

confirms the scaffold (or your edited version of it) passes validation
standalone, without a full app project around it. See
[`validating-and-publishing`](/plugin/validating-and-publishing). From
there: [`writing-the-js-side`](/plugin/writing-the-js-side),
[`writing-the-kotlin-side`](/plugin/writing-the-kotlin-side), and
[`writing-the-swift-side`](/plugin/writing-the-swift-side) cover filling
in the scaffold for real.
