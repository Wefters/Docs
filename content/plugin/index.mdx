## Overview

A **Wefter Plugin** bridges web applications running inside a WebView with native operating system capabilities (camera, biometric authentication, secure hardware storage, Bluetooth, sensors, and native dialogs).

Each plugin pairs a lightweight TypeScript wrapper package (`src/index.ts`) with native source code for Android (`Kotlin`) and/or iOS (`Swift`), communicating over a high-performance bi-directional bridge.

```ts
import { invokeNative } from "@wefterjs/core";

// Typed, Promise-based native call from web application JS
const result = await invokeNative<{ granted: boolean }>("camera", "requestPermission");
```

<Callout type="info">
  **App Developer vs Plugin Author**: If you are an application developer adding an existing plugin to your app, refer
  to [`wefter add`](/cli/add). This section is dedicated to plugin authors building, testing, and publishing native
  Wefter plugins.
</Callout>

## Key Plugin Concepts

### 1. Bi-Directional Bridge Execution

Calls placed via `invokeNative(plugin, method, payload)` return standard JavaScript Promises. Under the hood, Wefter generates native dispatcher classes (`<Name>PluginDispatch`) during [`wefter sync`](/cli/sync) that route calls directly to annotated native methods (`@WefterMethod` in Kotlin, `// @WefterMethod` in Swift) with zero reflection overhead.

### 2. Zero-Overhead Push Events (`emit`)

Native plugins can push real-time data streams to JavaScript at any time (e.g. sensor readings, barcode scanner results, device orientation changes) using `emit(hookName, data)`. JavaScript listens via `registerHook(hookName, callback)`.

### 3. Native Manifest & Dependency Injection

Plugins declare native requirements in `plugin.json`. During `wefter sync`, the CLI automatically:

- Merges Android permissions into `AndroidManifest.xml` and iOS permissions into `Info.plist`.
- Injects Gradle dependencies into `build.gradle.kts` and Swift Package Manager (SPM) packages into `Package.swift`.
- Merges ProGuard obfuscation rules into `proguard-rules.pro`.

## Platform Availability & Parity

Wefter respects platform-native design patterns rather than forcing false abstractions:

- **Asymmetric Support**: A plugin does not need to support both platforms to be complete. An Android-only plugin (`android/` folder only) or an iOS-only plugin (`ios/` folder only) is fully valid.
- **Graceful Rejection**: If an app calls a plugin method on an unsupported platform (e.g. calling an Android-only plugin on iOS), `invokeNative` cleanly rejects the Promise with `WefterBridgeError` code `"UNKNOWN_PLUGIN"`.
- **Platform Specific APIs**: Android provides built-in `hasPermission` / `requestPermission` helpers on `WefterPlugin`, whereas iOS permissions are managed per-framework (`AVCaptureDevice`, `CLLocationManager`, `PHPhotoLibrary`) as mandated by Apple.
