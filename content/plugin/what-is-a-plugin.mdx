## Overview

A **Wefter Plugin** is an npm package containing a manifest file (`plugin.json`), a TypeScript client wrapper (`src/index.ts`), and native source code for Android (`Kotlin`) and/or iOS (`Swift`).

Plugins bridge the gap between web application JavaScript running inside a WebView and native operating system APIs.

---

## Physical Directory Anatomy

A Wefter plugin package contains the following structure:

```text
my-wefter-plugin/
├── package.json          # NPM package manifest (declares @wefterjs/core dependency)
├── plugin.json           # Wefter native manifest (permissions, native dependencies, method lists)
├── src/
│   └── index.ts          # TypeScript client wrapper exporting invokeNative calls
├── android/              # Native Kotlin source directory (optional)
│   └── MyPlugin.kt
└── ios/                  # Native Swift source directory (optional)
    └── MyPlugin.swift
```

---

## Valid Platform Configurations

Wefter plugins support three physical directory configurations:

<Steps>
  <Step>
    ### Dual-Platform Plugin (`android/` and `ios/`) Ships Kotlin and Swift native source code for both Android and iOS
    applications.
  </Step>
  <Step>
    ### Android-Only Plugin (`android/` only) Ships Kotlin native source code only. Calling this plugin from iOS rejects
    with `UNKNOWN_PLUGIN`.
  </Step>
  <Step>
    ### iOS-Only Plugin (`ios/` only) Ships Swift native source code only. Calling this plugin from Android rejects with
    `UNKNOWN_PLUGIN`.
  </Step>
</Steps>

### 1. Dual-Platform Plugin (`android/` and `ios/`)

Ships Kotlin and Swift native source code. Both Android and iOS applications can invoke native methods.

### 2. Android-Only Plugin (`android/` only)

Ships Kotlin source code only. Calling this plugin from an iOS application cleanly rejects with `WefterBridgeError` code `"UNKNOWN_PLUGIN"`.

### 3. iOS-Only Plugin (`ios/` only)

Ships Swift source code only. Calling this plugin from an Android application cleanly rejects with `WefterBridgeError` code `"UNKNOWN_PLUGIN"`.

<Callout type="info">
  **Validation Passing**: `wefter plugin validate` passes single-platform plugins without errors. A plugin does not need
  to support both platforms to be considered complete or publishable.
</Callout>

## When to Build a Native Plugin

Before creating a native plugin, evaluate whether your feature requires native OS integration:

### Use Standard Web APIs (No Plugin Needed)

If your application feature can be implemented using standard browser Web APIs, you do **not** need a native plugin:

- Remote HTTP requests → Use standard `fetch()` or `axios`.
- Local key-value storage → Use `localStorage` or `IndexedDB`.
- Real-time messaging → Use `WebSocket` or `EventSource`.
- Basic animations & UI → Use HTML5, CSS3, and JavaScript frameworks.

### Build a Wefter Plugin (Native Plugin Required)

Build a Wefter native plugin when your application requires access to operating system hardware or native SDKs:

- Hardware access (Camera, Barcode Scanners, Bluetooth LE, NFC, Biometric Sensors).
- Secure hardware storage (Android Keystore, iOS Keychain).
- Native OS UI components (Native permission dialogs, System Settings, Push Notifications).
- Background OS tasks and device telemetry.

<Callout type="tip">
  **The Browser Test**: Ask yourself: *"Could this feature execute inside a standard Chrome or Safari browser tab
  without native desktop/mobile permissions?"* If **yes**, write it in web JavaScript. If **no**, build a Wefter native
  plugin.
</Callout>
