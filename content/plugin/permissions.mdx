## Overview

Operating system permissions are required before plugins can use sensitive hardware or data (camera, location, contacts, microphone, photo library, notifications).

- **Declare** them in `plugin.json`: Android permissions in `permissions.android`, iOS usage descriptions in `permissions.ios`. Sync adds them to the manifest and `Info.plist`.
- **Report and ask** for them the same way in every plugin: methods `checkPermissions()` and `requestPermissions()`, which resolve to the state of each permission by a name the plugin chooses.

---

## Permission states

| State     | Meaning                                                                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `granted` | The app may use it.                                                                                                                                     |
| `prompt`  | Asking shows the system prompt.                                                                                                                         |
| `denied`  | Only the system settings can change it: the user declined for good, or the app doesn't declare it. Apps call `openAppSettings()` from `@wefterjs/core`. |
| `limited` | Partly granted, such as the photos the user picked (iOS limited library, Android 14 partial media access).                                              |

Apps use these to explain a permission before asking, or to send the user to the settings:

```typescript
import { openAppSettings } from "@wefterjs/core";
import { Scanner } from "@wefterjs/scanner";

const { camera } = await Scanner.checkPermissions();
if (camera === "denied") showSettingsHint(() => openAppSettings());
else if (camera === "prompt") await Scanner.requestPermissions();
```

`wefter plugin validate` warns when a plugin declares a runtime permission (a dangerous Android permission or an iOS usage description) but lacks `checkPermissions` or `requestPermissions`. Face ID is exempt: iOS asks for it on first use and can't report it beforehand.

## Android

`WefterPlugin` has:

| Member                                                        | Description                                                                                                                                                                                  |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checkPermissions(permissions): Map<String, PermissionState>` | Where each permission stands.                                                                                                                                                                |
| `requestPermissions(permissions) { states -> }`               | Asks for those that can still be asked for and reports where each stands afterwards, on the main thread. Requests from all plugins and the web page are queued, one system prompt at a time. |
| `openAppSettings()`                                           | Opens the app's page in the system settings.                                                                                                                                                 |
| `hasPermission(permission)`                                   | Whether it is granted.                                                                                                                                                                       |

Android only says whether a permission is granted and whether to explain it before asking again; the shell remembers which permissions were asked for, so it can tell "not asked yet" (`prompt`) from "declined for good" (`denied`). `PermissionState.toString()` is the JavaScript name.

```kotlin
class CameraPlugin(context: Context, dispatcher: BridgeDispatcher) : WefterPlugin(context, dispatcher) {
    private val camera = Manifest.permission.CAMERA

    @WefterMethod
    fun checkPermissions(payload: JSONObject, callback: (Result<Any>) -> Unit) {
        resolve(callback, JSONObject().put("camera", checkPermissions(listOf(camera))[camera].toString()))
    }

    @WefterMethod
    fun requestPermissions(payload: JSONObject, callback: (Result<Any>) -> Unit) {
        requestPermissions(listOf(camera)) { states ->
            resolve(callback, JSONObject().put("camera", states[camera].toString()))
        }
    }

    @WefterMethod
    fun open(payload: JSONObject, callback: (Result<Any>) -> Unit) {
        requestPermissions(listOf(camera)) { states ->
            if (states[camera] == PermissionState.GRANTED) startCamera(callback)
            else reject(callback, "PERMISSION_DENIED", "Camera permission was denied")
        }
    }
}
```

The older `requestPermission(activity, permission) { granted -> }` still works and goes through the same queue; it is deprecated.

<Callout type="info">
  **Audit Enforcement**: If a plugin declares dangerous Android permissions (such as `CAMERA`, `ACCESS_FINE_LOCATION`,
  `RECORD_AUDIO`, `READ_CONTACTS`), `wefter plugin validate` verifies that Kotlin code contains explicit
  `"PERMISSION_DENIED"` error handling.
</Callout>

## iOS

Each framework asks for its own permission. `PermissionState` converts the common statuses, so plugins report them the same way:

| Initializer                              | From                               |
| ---------------------------------------- | ---------------------------------- |
| `PermissionState(AVAuthorizationStatus)` | Camera, microphone                 |
| `PermissionState(CLAuthorizationStatus)` | Location                           |
| `PermissionState(PHAuthorizationStatus)` | Photo library (`limited` included) |
| `PermissionState(UNAuthorizationStatus)` | Notifications                      |

`openAppSettings()` (on `WefterPlugin`, or `Permissions.openAppSettings()`) opens the app's page in Settings.

```swift
final class CameraPlugin: WefterPlugin {
    // @WefterMethod
    func checkPermissions(payload: [String: Any], callback: @escaping (Result<Any, Error>) -> Void) throws {
        resolve(callback, data: ["camera": PermissionState(AVCaptureDevice.authorizationStatus(for: .video)).rawValue])
    }

    // @WefterMethod
    func requestPermissions(payload: [String: Any], callback: @escaping (Result<Any, Error>) -> Void) throws {
        guard AVCaptureDevice.authorizationStatus(for: .video) == .notDetermined else {
            try checkPermissions(payload: payload, callback: callback)
            return
        }
        AVCaptureDevice.requestAccess(for: .video) { [weak self] _ in
            self?.resolve(callback, data: ["camera": PermissionState(AVCaptureDevice.authorizationStatus(for: .video)).rawValue])
        }
    }
}
```

## The iOS Permission Crash Hazard

<Callout type="warn">
  **Fatal iOS App Termination**: Calling an iOS framework permission API (such as `AVCaptureDevice.requestAccess`) when
  the required usage description key (e.g. `NSCameraUsageDescription`) is missing from `Info.plist` will **immediately
  crash the entire application process**. It cannot be caught by Swift `do/catch` blocks.
</Callout>

### How Wefter Protects Your Application

During [`wefter build ios`](/cli/build) and [`wefter run ios`](/cli/run), Wefter performs an automated `Info.plist` audit check (`checkInfoPlistPermissionKeys`).

If a plugin requests native permissions but its required `Info.plist` key is missing, `wefter build` halts before invoking `xcodebuild`:

```text
[ERROR] iOS permission configuration check failed:
  - Missing "NSCameraUsageDescription" in Info.plist, required by plugin "@wefterjs/camera" — calling this permission's API will CRASH the app immediately. Run `wefter sync` to regenerate Info.plist.
```
