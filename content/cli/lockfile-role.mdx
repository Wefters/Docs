## Overview

`wefter.lock.json` is an automatically generated lockfile that records the exact versions and `sha256` native source integrity hashes of all declared plugins installed in your Wefter project.

Committed to version control alongside `package.json` and `wefter.config.json`, `wefter.lock.json` ensures deterministic, repeatable native builds across all development environments and CI/CD runners.

---

## Lockfile Schema Structure

Every successful [`wefter sync`](/cli/sync) writes or updates `wefter.lock.json` at your project root:

```json
{
  "plugins": {
    "@wefterjs/camera": {
      "resolved": "0.0.1",
      "integrity": "sha256-b74045472a2336e36fe54a6c9310507e5968064b597a269d963fbd296ebb2403"
    },
    "@wefterjs/device": {
      "resolved": "0.0.1",
      "integrity": "sha256-f49a154b791448f76332155e8964344078652495b95a269d963fbd296ebb2401"
    }
  },
  "syncedAt": "2026-08-14T09:44:05.704Z"
}
```

### Property Definitions

- **`resolved`**: The exact package `version` string read from the plugin's `package.json` at sync time.
- **`integrity`**: A `sha256` hash computed over the plugin's `plugin.json` manifest, version string, Kotlin source files (`android/*.kt`), and Swift source files (`ios/*.swift`).
- **`syncedAt`**: ISO timestamp indicating when the lockfile was written.

---

## Integrity Hashing Mechanics

The `integrity` string is generated by sorting and hashing the raw bytes of:

1. `plugin.json` content.
2. Plugin version string.
3. Every `.kt` Kotlin file under `android/` (sorted alphabetically).
4. Every `.swift` Swift file under `ios/` (sorted alphabetically).

This cryptographic digest guarantees that any manual edits to native plugin code or manifests in `node_modules` can be tracked and verified.

## Plugin Version Drift Detection

During [`wefter sync`](/cli/sync), Wefter compares currently installed plugin package versions in `node_modules` against `wefter.lock.json`:

<Steps>
  <Step>
    ### 1. Lockfile Check `wefter sync` checks if `wefter.lock.json` exists in
    the project root. If missing, it generates a new lockfile fresh.
  </Step>
  <Step>
    ### 2. Version & Hash Comparison Compares `node_modules` plugin versions and
    SHA-256 source file hashes against locked integrity values.
  </Step>
  <Step>
    ### 3. Drift Resolution - If hashes match: Proceed with sync operation. - If
    hashes drift without `--update-lock`: Halt with a Version Drift Error. - If
    `--update-lock` is passed: Recalculate hashes, update `wefter.lock.json`,
    and complete sync.
  </Step>
</Steps>

### Version Drift Failure Output

If a package manager command (e.g., `pnpm update` or `npm install`) updates a plugin package version without updating `wefter.lock.json`, `wefter sync` halts before modifying native files:

```text
[ERROR] Plugin version drift detected against wefter.lock.json:
  - @wefterjs/camera: locked at 0.0.1, found 0.0.2
[INFO] Run `wefter sync --update-lock` if this is expected.
```

## Resolving Lockfile Drift

There are two recommended ways to accept and resolve lockfile drift:

### 1. Update Lockfile Flag (`--update-lock`)

Run `wefter sync` with the `--update-lock` flag to accept installed plugin versions and rewrite `wefter.lock.json`:

```bash
wefter sync --update-lock
```

### 2. Clean Baseline Regeneration

Delete `wefter.lock.json` and run `wefter sync`. When no lockfile exists, Wefter treats the operation as an initial sync and generates a fresh `wefter.lock.json`:

```bash
rm wefter.lock.json
wefter sync
```

---

## VCS & Version Control Best Practices

- **Always Commit**: Commit `wefter.lock.json` to Git alongside `package.json` and `wefter.config.json`.
- **CI Enforcement**: Run `wefter sync` in CI build pipelines without `--update-lock`. If dependencies drifted unexpectedly, CI will fail fast before compiling native binaries.
