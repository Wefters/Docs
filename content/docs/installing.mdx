---
title: Installing
description: Wrapping an existing web app with Wefter, start to running app.
---

Wefter wraps an existing web app, it doesn't scaffold a new one. If you
don't already have a Vue, React, Angular, or Svelte project (or anything
else that produces a static build) with its own `package.json`, start
that project first; everything below assumes it already exists. This page
also assumes you've already worked through [Environment
Setup](/docs/environment-setup) and have a working JDK, Android SDK, and a
device or emulator ready to go.

## 1. Run `wefter init`

From your project root, next to `package.json`:

```bash
npx wefter init
```

You don't need to have installed anything first. `npx` fetches
`@wefterjs/cli` temporarily to run this one command (see [Installing and
Running](/cli/installing-and-running) for that behavior in general).
`init` itself asks three questions, App ID, app name, and your web build
output directory, each pre-filled with a default guessed from
`package.json`'s `name`, accept with Enter or type your own:

```
App ID (reverse-DNS) (dev.local.myapp):
App name (Myapp):
Web build output directory (dist):
```

From those three answers, `init` writes `wefter.config.json`, adds
`@wefterjs/core` to `dependencies` and `@wefterjs/cli` to
`devDependencies` (both pinned to the exact CLI version that ran `init`)
and installs them through whichever package manager your project already
uses, and writes `WEFTER_APP_ID`/`WEFTER_APP_NAME`/`WEFTER_WEB_DIR` to
`.env`. It refuses to run a second time in the same project rather than
overwrite anything, and rolls back every file it touched if any step
fails partway through. Full behavior, including exactly what gets
written and every way it can refuse: [`wefter init`](/cli/init).

The config it writes looks like this:

```json
{
  "webDir": "dist",
  "environments": {
    "development": { "appId": "dev.local.myapp", "appName": "Myapp" }
  },
  "plugins": []
}
```

`webDir` is the folder `sync` copies into the native app as its bundled
assets. The `development` entry under `environments` carries its own
Android application ID, which is what makes a development build and a
production build two separate, independently installable apps on the
same device rather than one app that keeps overwriting itself every time
you rebuild. `init` only ever writes the one `development` environment;
add a `production` entry (and any others) by hand when you need one, see
the full [App Configuration reference](/docs/app-configuration).

`plugins` starts empty, and stays that way until you explicitly run
`wefter add` against a package. Wefter doesn't scan your `node_modules`
looking for anything that might be a plugin, so this array is your
project's complete, honest list of every native capability the app can
reach.

## 2. Sync

```bash
wefter sync
```

This is the step that turns config into an actual native project. It
recreates the Android shell from scratch under `.wefter/native/`, copies
your built web assets in, weaves in whatever plugins you've declared,
merges their Gradle dependencies and Android permissions, and writes out
`wefter.lock.json` recording exactly which plugin versions went in.

That directory is disposable. You never hand-edit anything inside
`.wefter/native/`, because the next `sync` throws it away and rebuilds it
fresh from your config. If you ever need to hand-edit the native project
directly, that's what `wefter eject` is for, and it's a one-way door, not
something you'd reach for by default.

## 3. Run it

```bash
wefter run android --watch
```

This builds the app, installs it on whatever device or emulator is
currently connected, and launches it. With `--watch`, the app's WebView
points at a live local dev server instead of the bundled files, so editing
your code and saving reflects on the device in well under a second, the
same hot reload you'd get from Vite in a browser tab.

Once it's running, [Development Workflow](/docs/development-workflow)
covers the rest of the day-to-day loop: when to reach for a plain `sync`,
when you need a full `build`, and what happens if the dev server becomes
unreachable mid-session.
