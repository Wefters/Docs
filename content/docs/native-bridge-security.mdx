## Overview

Wefter applications execute web code inside a native OS WebView (`android.webkit.WebView` and `WKWebView`) while exposing operating system capabilities through the native bridge (`window.AndroidBridge` and `window.webkit.messageHandlers.WefterBridge`).

Understanding the security boundaries between web JavaScript and native OS APIs is critical for shipping secure mobile applications.

---

## 1. WebView Security Boundaries

### Local Asset Isolation

When running in production, Wefter loads pre-compiled web assets bundled directly inside the application binary (`webDir`).

- **Android**: Assets are loaded locally via Android Asset Loader (`file:///android_asset/` or custom `WebViewAssetLoader` scheme).
- **iOS**: Assets are served through a custom local scheme handler (`WKURLSchemeHandler`), isolating local assets from external web origins.

### JavaScript Bridge Access

Any JavaScript running in the app's own pages (the bundled app, or the dev server during `wefter run --watch`) can call `invokeNative(plugin, method, payload)`, in any frame of those pages.

Pages from other origins can't. Both shells check the origin of every call, comparing scheme, host and port:

- **Android**: the bridge is a message channel the web view only adds to the app's own origins (`addWebMessageListener`), and each call is checked again against the origin the web view reports. Android System WebView 82 or newer is required; on older versions the app asks the user to update it.
- **iOS**: each message's `frameInfo.securityOrigin` is checked, and results go back only to the frame that called.
- A site in an iframe gets nothing, unless `frames.plugins` in `wefter.config.json` grants its exact origin specific plugin methods; calls outside the grant fail with `FORBIDDEN_ORIGIN`, and the built-in `__system` module is never reachable. Web windows never get the bridge. See [Embedded Sites](/docs/app-configuration/embedded-sites).

<Callout type="warn">
  **Dependency Auditing Warning**: Because any JS running in your WebView can invoke declared native plugin methods,
  treat third-party frontend npm packages with the same care as native dependencies.
</Callout>

## 2. Content Security Policy (CSP) Guidelines

The bundled files are already served with a Content Security Policy that only runs the app's own scripts, allows images, media and network requests over HTTPS and from the page's own `blob:` and `data:` URLs, and lets frames show only the app's own pages and the sites in `frames.allow` (see [Web APIs](/docs/app-configuration/web-apis#content-security-policy)). A policy in your `index.html` applies on top of it, so you can narrow it further.

Add a strict Content Security Policy (`<meta http-equiv="Content-Security-Policy">`) to your web application's `index.html` to restrict unauthorized external script execution:

```html
<!DOCTYPE html>
<html>
  <head>
    <meta charset="utf-8" />
    <meta
      http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; connect-src 'self' https://api.yourdomain.com;"
    />
    <title>Secure Wefter App</title>
  </head>
  <body>
    <div id="app"></div>
  </body>
</html>
```

### Recommended CSP Directives

- **`default-src 'self'`**: Restricts loading resources to bundled local app assets.
- **`script-src 'self'`**: Prevents injection of external remote scripts (`<script src="https://malicious.site/script.js">`).
- **`connect-src 'self' https://api.yourdomain.com`**: Restricts `fetch()` and `WebSocket` network calls to explicitly trusted backend APIs.

## 3. Native Navigation Restrictions

By default, Wefter configures WebViews to intercept navigation requests:

- **Internal Navigation**: Navigations within the app's own origin (the bundled app, or the dev server in debug builds) execute inside the WebView. `target="_blank"` and `window.open()` to the app's own pages load in place.
- **External Links**: Other sites open in the system browser, and `tel:`, `mailto:`, `sms:`, `intent:` and other app links in the app that handles them, so the main WebView never leaves the app's own pages. Frames inside a page load in place.
- **Blocked Schemes**: `javascript:`, `file:` and `content:` links are never handed to other apps. Android `intent:` links are limited to what a browser allows: no explicit component and no URI permission grants.
- **Device Access**: The camera, microphone and location are only given to the app's own pages, and only when the app declares them in `permissions`. See [Web APIs](/docs/app-configuration/web-apis).

## Security Best Practices Checklist

| Security Audit Item          | Recommended Configuration                                                      | Purpose                                                         |
| ---------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------- |
| **Strict CSP**               | Add `<meta http-equiv="CSP">` in `index.html`.                                 | Blocks Cross-Site Scripting (XSS) and remote script injections. |
| **Plugin Minimization**      | Declare only required plugins in `wefter.config.json`.                         | Minimizes exposed native API surface area.                      |
| **Input Payload Validation** | Validate native parameters using `guard let` (Swift) and JSON checks (Kotlin). | Prevents native crash exploits from malformed JS payloads.      |
| **HTTPS Endpoints Only**     | Enforce HTTPS for all API backend connections.                                 | Prevents Man-in-the-Middle (MitM) data tampering.               |
