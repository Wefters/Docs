## Overview

Developing a mobile application with Wefter involves three core CLI commands: [`wefter sync`](/cli/sync), [`wefter build`](/cli/build), and [`wefter run`](/cli/run).

Understanding when to run each command optimizes your development cycle and ensures clean native compilation.

---

## Core CLI Commands Comparison

| Command                       | Native Codegen & Manifest Weaving | Compiles Native Code          | Produces Binary Artifact   | Installs & Launches on Device |
| ----------------------------- | --------------------------------- | ----------------------------- | -------------------------- | ----------------------------- |
| **`wefter sync`**             | **Yes**                           | No                            | No (Manifests & Code only) | No                            |
| **`wefter build <platform>`** | **Yes** (calls `sync`)            | **Yes** (Gradle / xcodebuild) | **Yes** (`.apk` / `.app`)  | No                            |
| **`wefter run <platform>`**   | **Yes** (calls `sync`)            | **Yes** (calls `build`)       | **Yes**                    | **Yes** (via `adb` / `xcrun`) |

## 1. Fast Configuration Weaving: `wefter sync`

`wefter sync` is a fast, offline command that generates native projects inside `.wefter/native/android` and `.wefter/native/ios`:

- Reads `wefter.config.json` and resolves declared `plugins`.
- Verifies plugin package versions against `wefter.lock.json`.
- Copies compiled web assets from `webDir` into native asset directories.
- Weaves native Kotlin/Swift source files and substitutes package headers.
- Merges Gradle dependencies, ProGuard rules, Android manifest entries, and iOS `Info.plist` usage keys.
- Generates typed native registry dispatchers (`GeneratedRegistry.kt` and `GeneratedRegistry.swift`).

<Callout type="tip">
  **When to run `wefter sync`**: Run `sync` when editing `wefter.config.json`,
  adding local plugin files, or inspecting generated native project structures
  before starting a native compilation build.
</Callout>

## 2. Live Hot Reload Sessions: `wefter run <platform> --watch`

During active frontend development, launch a live hot reload session using the `--watch` flag:

```bash
# Android live hot reload
wefter run android --watch

# iOS live hot reload (macOS)
wefter run ios --watch
```

### How `--watch` Operates

1. Starts a local web dev server (e.g. Vite dev server) on your host machine.
2. Compiles a debug native application binary where the `WebView` URL points to your dev server URL instead of local static assets.
3. Installs and launches the application on your connected physical ADB device, Android emulator, or iOS Simulator.
4. Any changes saved to your web UI (HTML, CSS, JS, Vue, React, Svelte) reflect **instantaneously** inside the mobile app without requiring native re-installation.

<Callout type="warn">
  **Dev Server Disconnection**: If the web dev server is closed, the app displays a clear `"Dev server unreachable"` diagnostic overlay rather than failing silently with stale assets. Restart `wefter run <platform> --watch` to reconnect.
</Callout>

## 3. Environment Scoping: `--env <name>`

`wefter.config.json` supports multiple named build environments (e.g. `development`, `staging`, `production`), each with unique application IDs (`appId`):

```bash
# Run production environment build
wefter run android --env production
```

Because each environment carries a distinct Android application ID and iOS bundle ID, development and production builds can co-exist side-by-side on the same physical device without overwriting each other.

---

## 4. Production Release Builds

Before producing production artifacts for App Store or Google Play deployment:

1. **Verify Release Environment**:
   ```bash
   wefter doctor --release-readiness
   ```
2. **Build Signed Release Binary**:

   ```bash
   # Android release APK
   wefter build android --release --env production

   # iOS release build
   wefter build ios --release --env production
   ```
